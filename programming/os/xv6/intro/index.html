    Точка входа¶

    make - утилита автоматизации сборки программ, которая выполняет правила сборки и команды, описанные в Makefile. В качестве аргумента принимает цель а также поддерживает некоторые флаги.

    QEMU - программный эмулятор и визуализатор аппаратных платформ, позволяющий запускать операционные системы и программы для различных архитектур процессоров

    Makefile - текстовый файл, содержащий правила, зависимости и команды, которые использует программа make

    Основное правило для Makefile:

    цель: зависимости цели

    команды которые нуно выполнить

    Непосредственно у нас это выглядит следующим обазом:

    qemu: $K/kernel fs.img

    qemu-system-riscv64 -machine virt -bios none -kernel kernel/kernel -m 128M -smp 3 -nographic -global virtio-mmio.force-legacy=false -drive file=fs.img,if=none,format=raw,id=x0 -device virtio-blk-device,drive=x0,bus=virtio-mmio-bus.0

    где:

    qemu-system-riscv64 — запустить эмулятор 64-битной RISC-V-машины.

    -machine virt — использовать стандартную виртуальную плату QEMU virt.

    -bios none — не загружать отдельный BIOS/firmware-файл.

    -kernel kernel/kernel — загрузить собранное ядро xv6.

    -m 128M — предоставить виртуальной машине 128 МиБ оперативной памяти.

    -smp 3 — создать три виртуальных процессорных контекста — hart.

    -nographic — работать без графического окна, используя текущий терминал как консоль.

    -global virtio-mmio.force-legacy=false — использовать современный режим интерфейса virtio-MMIO.

    -drive file=fs.img,if=none,format=raw,id=x0 — создать дисковый backend x0 из сырого образа fs.img, пока не подключая его автоматически.

    -device virtio-blk-device,drive=x0,bus=virtio-mmio-bus.0 — подключить backend x0 как виртуальное блочное устройство к плате.

    Итог

    QEMU создаёт виртуальный RISC-V-компьютер с тремя hart, 128 МиБ RAM, ядром kernel/kernel, диском fs.img и консолью, подключённой к текущему терминалу.

    Разбор Makefile¶

    В начале Makefile определены:

    K=kernel
U=user

    Они не являются:

    • переменными C;
    • переменными shell;
    • переменными работающего ядра xv6.

    Они существуют только во время обработки Makefile.

    Обращение к переменной

    Обычная форма:

    $(K)

    Также допустима:

    ${K}

    Для однобуквенного имени разрешена сокращённая запись:

    $K

    Для многобуквенных имён скобки необходимы:

    $(OBJS)
$(CFLAGS)
$(QEMU)
$(QEMUOPTS)

    Запись:

    $OBJS

    не означает переменную OBJS: Make воспримет только $O как однобуквенную переменную.

    Оператор =

    Строка:

    K=kernel

    использует оператор =.

    Он создаёт рекурсивно раскрываемую, или ленивую, переменную. Make сохраняет выражение справа и раскрывает вложенные переменные в момент использования.

    Например:

    A = $(B)
B = hello

    При использовании:

    $(A)

    получится:

    hello

    Для K=kernel разница между ленивым и немедленным раскрытием несущественна, поскольку справа нет других переменных.

    Состав ядра в Makefile¶

    Основной список объектных файлов задан переменной:

    OBJS = \
  $K/entry.o \
  $K/kalloc.o \
  $K/string.o \
  $K/main.o \
  $K/vm.o \
  $K/proc.o \
  $K/swtch.o \
  $K/trampoline.o \
  $K/trap.o \
  $K/syscall.o \
  $K/sysproc.o \
  $K/bio.o \
  $K/fs.o \
  $K/log.o \
  $K/sleeplock.o \
  $K/file.o \
  $K/pipe.o \
  $K/exec.o \
  $K/sysfile.o \
  $K/kernelvec.o \
  $K/plic.o \
  $K/virtio_disk.o

    Важно

    OBJS можно рассматривать как список имён файлов: 

    kernel/entry.o kernel/kalloc.o kernel/main.o ...

    Но технически Make хранит его как строку из слов, разделённых пробелами.

    Это не массив в смысле C, C++ или Python.

    Объектные файлы¶

    Файл с расширением .o — отдельно собранная часть будущего ядра.

    Для C:

    kernel/main.c
    ↓ compiler
kernel/main.o

    Для assembly:

    kernel/entry.S
    ↓ assembler
kernel/entry.o

    объектный файл уже содержит часть машинного кода и данных, но ещё не является полным ядром.

    Позднее линковщик объединит объектные файлы:

    entry.o
kalloc.o
main.o
vm.o
proc.o
...
    ↓ linker
kernel/kernel

    Внутреннее устройство объектных файлов на данном этапе не рассматривается.

    Группы объектных файлов¶

    На начальном уровне файлы можно разделить по назначению.

    Запуск и базовые функции

    entry.o
kalloc.o
string.o
main.o
    • entry.o — начальный код xv6;
    • kalloc.o — управление свободными физическими страницами;
    • string.o — базовые операции над памятью и строками;
    • main.o — последовательность инициализации ядра.

    Память и выполнение программ 

    vm.o
proc.o
swtch.o

    • vm.o — работа с отображениями памяти;
    • proc.o — структуры и жизненный цикл выполняющихся программ;
    • swtch.o — низкоуровневое переключение сохранённого состояния выполнения.

    Переходы в ядро и системные вызовы 

    trampoline.o
trap.o
syscall.o
sysproc.o
kernelvec.o

    • trampoline.o — низкоуровневый переход между пользовательским кодом и ядром;
    • trap.o — обработка событий, передающих управление ядру;
    • syscall.o — выбор реализации системного вызова;
    • sysproc.o — системные вызовы, связанные с выполнением программ;
    • kernelvec.o — сохранение состояния при событии внутри ядра.

    Файловая подсистема

    bio.o
fs.o
log.o
sleeplock.o
file.o
pipe.o
exec.o
sysfile.o

    Их внутреннее устройство будет разобрано позднее, после памяти, процессов и системных вызовов.

    Устройства

    plic.o
virtio_disk.o
    • plic.o — получение событий от внешних устройств;
    • virtio_disk.o — взаимодействие с виртуальным диском QEMU.

    Переменная OBJS_KCSAN

    Отдельно задан список:

    OBJS_KCSAN = \
  $K/start.o \
  $K/console.o \
  $K/printf.o \
  $K/uart.o \
  $K/spinlock.o

    Эти объектные файлы входят в kernel даже при выключенном KCSAN.

    Итоговый набор частей ядра:

    $(OBJS) + $(OBJS_KCSAN)

    Краткие роли:

    • start.o — ранняя настройка RISC-V перед переходом в main();
    • console.o — общий интерфейс консоли xv6;
    • printf.o — форматированный вывод из ядра;
    • uart.o — взаимодействие с виртуальным последовательным устройством;
    • spinlock.o — низкоуровневая блокировка для нескольких hart.

    Порядок объектных файлов не равен порядку выполнения

    В порядке линковки start.o расположен после main.o, но фактическое выполнение идёт так:

    entry
↓
start
↓
main

    Порядок выполнения задаётся машинными инструкциями переходов и вызовов.

    Порядок объектных файлов влияет на размещение их содержимого внутри итогового файла, но сам по себе не задаёт control flow.

    Условная сборка KCSAN

    В Makefile:

    ifdef KCSAN
OBJS_KCSAN += \
    $K/kcsan.o
endif

    KCSAN — Kernel Concurrency Sanitizer.

    На текущем уровне:

    KCSAN — дополнительный режим сборки, помогающий обнаруживать небезопасные одновременные обращения к памяти.

    ifdef KCSAN — условие GNU Make.

    При обычном:

    make qemu

    kernel/kcsan.o обычно не добавляется.

    При:

    make KCSAN=1 qemu

    переменная KCSAN получает значение 1, поэтому выполняется:

    OBJS_KCSAN += $K/kcsan.o

    Оператор += добавляет значение к уже существующей переменной.

    Текущее состояние графа

    После рассмотренной части Makefile известна следующая схема:

    K = kernel
U = user
    │
    ├── OBJS
    │   ├── entry.o
    │   ├── kalloc.o
    │   ├── main.o
    │   ├── vm.o
    │   ├── proc.o
    │   ├── filesystem objects
    │   └── device objects
    │
    └── OBJS_KCSAN
        ├── start.o
        ├── console.o
        ├── printf.o
        ├── uart.o
        ├── spinlock.o
        └── kcsan.o при KCSAN=1

    Эти объектные файлы позднее будут объединены в:

    kernel/kernel

    После подготовки kernel/kernel и fs.img Make выполнит:

    qemu-system-riscv64 ...

    и запустит виртуальную машину.

    Полный процесс сборки¶

    После определения OBJS и OBJS_KCSAN Make знает, из каких частей должно состоять ядро:

    kernel/entry.o
kernel/kalloc.o
kernel/string.o
kernel/main.o
kernel/vm.o
kernel/proc.o
...
kernel/start.o
kernel/console.o
kernel/printf.o
kernel/uart.o
kernel/spinlock.o

    Эти файлы пока ещё не являются ядром. Каждый .o представляет только отдельно собранную часть будущего kernel/kernel.

    Полная последовательность выглядит так:

    исходные файлы kernel/*.c и kernel/*.S
                    ↓
          отдельные объектные файлы
                    ↓
            работа линковщика
                    ↓
             kernel/kernel
                    ↓
       загрузка файла программой QEMU
                    ↓
         начало выполнения в _entry

    Компиляция C-файла¶

    Для C-файлов Make использует следующее:

    Makefile 102 строка
    $K/%.o: $K/%.c
    $(CC) $(CFLAGS) $(EXTRAFLAG) -c -o $@ $<

    Символ % обозначает одинаковую переменную часть имени.

    Если Make требуется файл:

    kernel/main.o

    то:

    % → main

    и правило превращается в:

    kernel/main.o: kernel/main.c
    $(CC) $(CFLAGS) $(EXTRAFLAG) \
        -c -o kernel/main.o kernel/main.c

    Автоматические переменные здесь означают:

    $@ → имя цели       → kernel/main.o
$< → первая зависимость → kernel/main.c

    Флаг -c у компилятора означает:

    Обработать исходный файл и создать объектный файл, но не пытаться собрать всю программу целиком.

    По этому правилу независимо создаются:

    kernel/main.c   → kernel/main.o
kernel/vm.c     → kernel/vm.o
kernel/proc.c   → kernel/proc.o
kernel/kalloc.c → kernel/kalloc.o

    Полный путь одного C-файла включает три основные стадии:

    kernel/main.c
       ↓ C preprocessor
обработанный исходный текст
       ↓ compiler
assembly RISC-V
       ↓ assembler
kernel/main.o

    C препроцессор раскрывает:

    #include
#define
#ifdef

    компилятор преобразует результат в assembly RISC-V, а ассемблер кодирует assembly-инструкции в машинные инструкции и помещает их в объектный файл.

    Для файлов .S, например kernel/entry.S, Make использует встроенное правило GNU Make. Фактически выполняется команда вида:

    riscv64-linux-gnu-gcc -c \
    -o kernel/entry.o kernel/entry.S

    Расширение .S означает assembly source, который перед ассемблированием может проходить через препроцессор C. GCC здесь действует как управляющая программа и при необходимости вызывает препроцессор и ассемблер.

    В результате:

    kernel/entry.S      → kernel/entry.o
kernel/swtch.S      → kernel/swtch.o
kernel/trampoline.S → kernel/trampoline.o
kernel/kernelvec.S  → kernel/kernelvec.o

    Как main.c может вызывать функции из других файлов

    В kernel/main.c находятся вызовы:

    kinit();
kvminit();
procinit();
trapinit();
plicinit();
binit();
iinit();
fileinit();
virtio_disk_init();
userinit();
scheduler();

    Но реализации этих функций находятся в других файлах:

    kinit             → kernel/kalloc.c
kvminit           → kernel/vm.c
procinit          → kernel/proc.c
trapinit          → kernel/trap.c
plicinit          → kernel/plic.c
binit             → kernel/bio.c
iinit             → kernel/fs.c
fileinit          → kernel/file.c
virtio_disk_init  → kernel/virtio_disk.c
userinit          → kernel/proc.c
scheduler         → kernel/proc.c

    Во время компиляции main.c компилятор не обязан видеть тела этих функций. Ему достаточно их объявлений из заголовочного файла kernel/defs.h.

    Например, defs.h сообщает компилятору приблизительно следующее:

    void kinit(void);
void kvminit(void);
void procinit(void);
void userinit(void);
void scheduler(void);

    Объявление функции сообщает:

    • имя функции;
    • тип возвращаемого значения;
    • количество и типы аргументов.

    Благодаря этому компилятор может проверить корректность вызова и сформировать машинную инструкцию вызова.

    Однако при отдельной компиляции main.c ещё неизвестно, по какому итоговому адресу будет находиться kinit() или userinit(). Их размещение станет известно только после объединения всех объектных файлов.

    Поэтому внутри main.o фактически остаётся информация следующего смысла:

    в этом месте нужно вызвать kinit;
в этом месте нужно вызвать userinit;
точные адреса должен определить линковщик.

    Соответствующие определения находятся в других объектных файлах:

    main.o:
    определяет main
    использует kinit
    использует userinit
    использует scheduler

kalloc.o:
    определяет kinit

proc.o:
    определяет userinit
    определяет scheduler

    Место объектного файла, которое зависит от ещё неизвестного адреса, сопровождается специальной записью для линковщика. Такая запись называется реллокацией.

    На данном уровне достаточно следующего определения:

    Реллокация указывает линковщику, какое место машинного кода или данных нужно исправить после вычисления окончательного адреса функции.

    В результате компилятор может отдельно собрать main.o, не зная физических адресов функций из остальных файлов. Эти адреса позднее вычислит линковщик.

    Что находится в объектном файле

    объектный файл содержит не только машинные инструкции. Его содержимое разделяется на логические области — секции.

    Основными секции являются:

    .text
.rodata
.data
.bss

    .text содержит машинные инструкции:

    main.o:.text   → инструкции функции main()
vm.o:.text     → инструкции функций виртуальной памяти
entry.o:.text  → инструкции _entry

    Несмотря на название text, здесь хранится не исходный текст программы, а исполняемый машинный код.

    .rodata, то есть read-only data, содержит данные, которые существуют в памяти, но не должны изменяться.

    Например:

    printf("xv6 kernel is booting\n");

    После компиляции разделяется на две части:

    .text:
инструкции, подготавливающие вызов printf

.rodata:
байты строки "xv6 kernel is booting\n"

    .data содержит изменяемые глобальные и статические объекты с заданным ненулевым начальным значением.

    Например:

    int value = 6777119;

    Число 6777119 должно физически находиться в собранном файле, чтобы при загрузке переменная уже имела это значение.

    В xv6 в .data находится, например, массив initcode[], содержащий конкретные машинные байты первого маленького пользовательского кода.

    .bss содержит глобальные и статические объекты, начальное значение которых равно нулю.

    Например:

    volatile static int started = 0;

    Также в .bss находятся крупные массивы:

    struct proc proc[NPROC];
char stack0[4096 * NCPU];

    Для .bss нет необходимости хранить в исполняймом файле тысячи нулевых байтов. Достаточно записать размер области и требование создать её с нулевым начальным содержимым.

    Поэтому .bss:

    занимает место в памяти после загрузки;
не требует хранения всех своих нулей в файле.

    Упрощённо kernel/main.o можно представить так:

    kernel/main.o
├── .text
│   └── машинные инструкции main()
├── .rodata
│   └── строки для printf
├── .data
│   └── данные с ненулевым начальным значением
├── .bss
│   └── started
├── таблица имён
└── информация о местах, которые должен исправить линковщик

    Каждый объектный файл содержит собственные секции. До линковки существуют:

    entry.o:.text
main.o:.text
vm.o:.text
proc.o:.text
start.o:.text
...

    Они ещё не образуют одну непрерывную область ядра.

    Линковка ядра¶

    Правило создания итогового ядра выглядит так:

    $K/kernel: $(OBJS) $(OBJS_KCSAN) $K/kernel.ld $U/initcode
    $(LD) $(LDFLAGS) -T $K/kernel.ld -o $K/kernel $(OBJS) $(OBJS_KCSAN)
    $(OBJDUMP) -S $K/kernel > $K/kernel.asm
    $(OBJDUMP) -t $K/kernel | sed '1,/SYMBOL TABLE/d; s/ .* / /; /^$$/d' > $K/kernel.sym

    После раскрытия переменных первая строка имеет следующий смысл:

    kernel/kernel:
    все объектные файлы ядра
    kernel/kernel.ld
    user/initcode

    kernel/kernel — цель, а всё после двоеточия — зависимости. Всё прям как говорилось вначале

    Make сначала убеждается, что каждая зависимостей существует и актуальна. Если хотя бы один из них новее kernel/kernel, ядро нужно пересобрать.

    $(LD) $(LDFLAGS) -T $K/kernel.ld -o $K/kernel $(OBJS) $(OBJS_KCSAN)

    на нашей системе приблизительно раскрывается так:

    riscv64-linux-gnu-ld \
    -z max-page-size=4096 \
    -T kernel/kernel.ld \
    -o kernel/kernel \
    kernel/entry.o \
    kernel/kalloc.o \
    kernel/string.o \
    kernel/main.o \
    kernel/vm.o \
    kernel/proc.o \
    ... \
    kernel/start.o \
    kernel/console.o \
    kernel/printf.o \
    kernel/uart.o \
    kernel/spinlock.o

    ld — линковщик.

    Флаг:

    -T kernel/kernel.ld - описание структуры и размещения ядра при линковке

    Флаг:

    -o kernel/kernel

    задаёт имя выходного файла.

    Затем передаётся полный список объектных файлов, а линковщик выполняет несколько связанных задач:

    Во-первых, он объединяет одноимённые входные секции в порядке их объявления:

    entry.o:.text ─────┐
kalloc.o:.text ────┤
main.o:.text ──────┤
vm.o:.text ────────┤
proc.o:.text ──────┤
start.o:.text ─────┤
                   ├──→ kernel/kernel:.text
остальные .text ───┘

    Аналогично:

    все *.o:.rodata → kernel/kernel:.rodata
все *.o:.data   → kernel/kernel:.data
все *.o:.bss    → kernel/kernel:.bss

    Во-вторых, линковщик сопоставляет использования имена с их определениями:

    main.o использует kinit
kalloc.o определяет kinit
        ↓
линковщик связывает их

main.o использует userinit
proc.o определяет userinit
        ↓
линковщик связывает их

entry.o использует start
start.o определяет start
        ↓
линковщик связывает их

    В-третьих, линковщик назначает итоговые адреса и применяет реллокации. После того как линковщик решил, где будет находиться каждая функция, он исправляет инструкции вызовов и другие места, зависящие от адресов.

    После линковки отдельная граница исходных файлов уже не определяет возможность вызова:

    entry.S может вызвать start() из start.c;
start.c может передать управление main() из main.c;
main.c может вызвать kinit() из kalloc.c;
main.c может вызвать userinit() из proc.c.

    Все эти функции теперь находятся внутри одного связанного образа:

    kernel/kernel

    Почему порядок объектные файлы имеет значение

    объектные файлы передаются линковщику в определённом порядке:

    OBJS = \
  $K/entry.o \
  $K/kalloc.o \
  $K/string.o \
  $K/main.o \
  ...

    entry.o расположен первым. Это важно для размещения начального кода.

    kernel.ld собирает входные .text в общую выходную .text:

    .text : {
  *(.text .text.*)
  ...
}

    Входные секции обычно добавляются в порядке объектных файлов, переданных линковщику. Поэтому сначала в общую .text попадает:

    entry.o:.text

    а затем:

    kalloc.o:.text
string.o:.text
main.o:.text
...

    В entry.o:.text первым глобальным именем является:

    _entry

    Одновременно kernel.ld устанавливает начало общей .text по адресу:

    0x80000000

    Получается:

    .text ядра начинается с 0x80000000
        +
первой добавляется .text из entry.o
        +
в начале entry.o находится _entry
        ↓
_entry получает адрес 0x80000000

    Это конкретная причина, по которой расположение entry.o в списке важно.

    Но порядок объектных файлов не является порядком выполнения функций.

    Например, main.o передаётся линковщику раньше start.o, однако выполнение идёт так:

    _entry
   ↓ call
start
   ↓ mret
main

    Порядок выполнения задают машинные инструкции переходов и вызовов. Порядок объектных файлов влияет прежде всего на размещение их содержимого и итоговые адреса.

    Как kernel.ld управляет итоговым расположением¶

    Команда linker использует:

    -T $K/kernel.ld

    Файл kernel/kernel.ld содержит правила размещения:

    OUTPUT_ARCH("riscv")
ENTRY(_entry)

SECTIONS
{
  . = 0x80000000;

  .text : {
    *(.text .text.*)
    . = ALIGN(0x1000);
    _trampoline = .;
    *(trampsec)
    . = ALIGN(0x1000);
    ASSERT(. - _trampoline == 0x1000,
           "error: trampoline larger than one page");
    PROVIDE(etext = .);
  }

  .rodata : {
    . = ALIGN(16);
    *(.srodata .srodata.*)
    . = ALIGN(16);
    *(.rodata .rodata.*)
  }

  .data : {
    . = ALIGN(16);
    *(.sdata .sdata.*)
    . = ALIGN(16);
    *(.data .data.*)
  }

  .bss : {
    . = ALIGN(16);
    *(.sbss .sbss.*)
    . = ALIGN(16);
    *(.bss .bss.*)
  }

  PROVIDE(end = .);
}

    Директива:

    OUTPUT_ARCH("riscv")

    говорит линковщику, для какой архитектуры мы собираем бинарный файл, тк он должен знать формат инструкций и размеры указателей (в нашем случае 64-битный RISC-V). Это гарантирует, что итоговый файл kernel будет иметь правильный заголовок ELF, который QEMU сможет распознать как исполняемый код для RISC-V.

    Строка:

    ENTRY(_entry)

    устанавливает точку входа в программу. Внутри ELF-файла ядра есть поле Entry point address. Линковщик запишет туда адрес метки _entry (entry.S). Хоть QEMU и так прыгает на 0x80000000, наличие явной точки входа позволяет отладчикам (GDB) и загрузчикам точно знать, с какой инструкции начинается выполнение логики.

    Блок:

    SECTIONS
{
    ...
}

    задаёт расположение выходных секций.

    Специальный символ:

    .

    в линк-скриптах называется Location Counter (счетчик адреса - текущее положение головки). Мы принудительно устанавливаем его в 0x80000000.

    Строка:

    . = 0x80000000;

    устанавливает начальный адрес размещения ядра:

    0x80000000

    После этого создаётся итоговая .text:

    .text : {
  *(.text .text.*)
  ...
}

    Выражение:

    *(.text .text.*)

    означает:

    Из всех переданных объектных файлов взять входные секции .text и .text.* и добавить их в итоговую .text.

    Звёздочка перед скобками означает любой входной файл, а .text.* охватывает дополнительные секции, имена которых начинаются с .text..

    В середине .text отдельно размещается код trampoline:

    . = ALIGN(0x1000);
_trampoline = .;
*(trampsec)
. = ALIGN(0x1000);

    ALIGN(0x1000) округляет текущий адрес вверх до границы, кратной:

    0x1000 = 4096 байт

    После первого выравнивания линковщик создаёт переменную:

    _trampoline

    равный текущему адресу.

    Затем:

    *(trampsec)

    помещает сюда специальную входную секцию trampsec из trampoline.S.

    После неё адрес снова выравнивается на 4096 байт.

    Проверка:

    ASSERT(. - _trampoline == 0x1000,
       "error: trampoline larger than one page");

    требует, чтобы зарезервированная область trampoline занимала ровно одну страницу. Если код перестанет помещаться в одну страницу, линковщик остановит сборку.

    Почему trampoline должна занимать отдельную страницу, станет понятно при разборе перехода между user mode и kernel mode. Пока важно только зафиксировать:

    kernel.ld помещает trampoline на границу страницы
и проверяет её размер во время линковки.

    В конце .text создаётся переменная:

    PROVIDE(etext = .);

    etext обозначает адрес сразу после области исполняемого кода ядра.

    Позднее vm.c использует его для разделения прав памяти:

    от начала kernel до etext:
код ядра — чтение и выполнение

от etext далее:
данные ядра — чтение и запись

    После .text линковщик формирует .rodata:

    .rodata : {
  . = ALIGN(16);
  *(.srodata .srodata.*)
  . = ALIGN(16);
  *(.rodata .rodata.*)
}

    Сюда собираются read-only data из всех объектных файлов. ALIGN(16) выравнивает текущий адрес на границу, кратную 16 байтам.

    Затем формируется .data:

    .data : {
  . = ALIGN(16);
  *(.sdata .sdata.*)
  . = ALIGN(16);
  *(.data .data.*)
}

    Сюда попадают изменяемые глобальные данные с сохранёнными начальными значениями.

    После неё формируется .bss:

    .bss : {
  . = ALIGN(16);
  *(.sbss .sbss.*)
  . = ALIGN(16);
  *(.bss .bss.*)
}

    Сюда попадают нулевые глобальные и статические данные.

    В самом конце:

    PROVIDE(end = .);

    создаётся пееменная end, равный первому адресу после всех размещённых частей ядра.

    Итоговую схему можно представить так:

    0x80000000 ┌──────────────────────────┐
           │ .text                    │
           │                          │
           │ машинный код ядра        │
           │                          │
           │ trampoline               │
     etext ├──────────────────────────┤
           │ .rodata                  │
           │ строковые константы      │
           ├──────────────────────────┤
           │ .data                    │
           │ данные с начальными      │
           │ значениями               │
           ├──────────────────────────┤
           │ .bss                     │
           │ нулевые глобальные       │
           │ объекты и массивы        │
       end └──────────────────────────┘

    etext и end не являются обычными переменными, определёнными в C-файле. Их значения создаёт линковщик.

    Тем не менее C-код может объявить их как внешние переменные и использовать их адреса.

    Например, kalloc.c использует end как границу:

    память до end занята самим kernel;
память после end можно начать передавать аллокатору.

    Таким образом, решение, принятое линковщиком во время сборки, позднее непосредственно используется работающим ядром.

    Что такое kernel/kernel¶

    Результат линковки:

    kernel/kernel

    является ELF-файлом.

    ELF — формат, который может содержать:

    • машинный код;
    • начальные данные;
    • описание их расположения;
    • адрес точки входа;
    • имена;
    • отладочную информацию.

    kernel/kernel — уже не объектный файл отдельного исходника. Это единый связанный исполняймый объект всего ядра xv6:

    kernel/kernel
├── код _entry
├── код start
├── код main
├── memory allocator
├── virtual memory
├── processes
├── traps
├── system calls
├── filesystem
├── drivers
├── read-only data
├── writable data
├── zero-initialized data
├── entry point
└── отладочная информация

    Слово executable здесь не означает, что файл можно запустить как обычную Linux-программу:

    ./kernel/kernel

    Внутри находится машинный код RISC-V, предназначенный для виртуальной RISC-V-машины и не рассчитанный на пользовательское окружение Linux.

    Листинги kernel.asm и kernel.sym

    После создания kernel/kernel Make выполняет:

    $(OBJDUMP) -S $K/kernel > $K/kernel.asm

    После раскрытия:

    riscv64-linux-gnu-objdump -S \
    kernel/kernel > kernel/kernel.asm

    objdump исследует уже созданный исполняемый файл.

    Флаг -S просит дизассемблировать машинный код и, если доступна отладочная информация, показать рядом строки исходного кода.

    Результат:

    kernel/kernel.asm

    позволяет связать:

    исходный код
    ↕
assembly
    ↕
машинное кодирование
    ↕
итоговый адрес

    Например, там можно увидеть:

    0000000080000000 <_entry>:
    80000000: 00009117  auipc sp,0x9

    Следующая команда:

    $(OBJDUMP) -t $K/kernel |
sed '1,/SYMBOL TABLE/d; s/ .* / /; /^$$/d' >
$K/kernel.sym

    сначала получает таблицу имен:

    objdump -t kernel/kernel

    затем sed удаляет заголовок, лишние поля и пустые строки.

    Внутри recipe Make запись:

    $$

    нужна для передачи shell одного символа $. Поэтому:

    /^$$/d

    после обработки Make превращается в:

    /^$/d

    и удаляет пустые строки.

    Результат:

    kernel/kernel.sym

    содержит компактную связь:

    адрес → имя

    Например:

    0x80000000 → _entry
адрес main → main
адрес kinit → kinit

    kernel.asm и kernel.sym не загружаются QEMU. Это производные файлы для изучения и отладки. QEMU получает именно kernel/kernel.

    Сборка обычных пользовательских программ¶

    Первый пользовательский код initcode

    В зависимостях ядра присутствует:

    $U/initcode

    Для его создания используется отдельная цепочка:

    $U/initcode: $U/initcode.S
    $(CC) $(CFLAGS) -march=rv64g -nostdinc -I. -Ikernel -c $U/initcode.S -o $U/initcode.o
    $(LD) $(LDFLAGS) -N -e start -Ttext 0 -o $U/initcode.out $U/initcode.o
    $(OBJCOPY) -S -O binary $U/initcode.out $U/initcode
    $(OBJDUMP) -S $U/initcode.o > $U/initcode.asm

    Последовательность:

    user/initcode.S
        ↓
user/initcode.o
        ↓
user/initcode.out
        ↓
user/initcode

    Первая команда создаёт объектный файл:

    user/initcode.S → user/initcode.o

    Вторая команда связывает его в маленький отдельный исполняймый образ:

    -e start
-Ttext 0

    -e start назначает метку start из user/initcode.S точкой входа этого маленького образа.

    Это не функция start() из kernel/start.c. Kernel и initcode связываются отдельно, поэтому одинаковые имена не конфликтуют.

    -Ttext 0 размещает код с адреса 0, потому что ядро позднее скопирует initcode в начало адресного пространства первого пользовательского процесса.

    Команда:

    $(OBJCOPY) -S -O binary $U/initcode.out $U/initcode

    убирает ELF-обёртку и оставляет сырые машинные байты.

    Итоговый user/initcode содержит маленькую последовательность, которая позднее запросит:

    exec("/init")

    В нашей версии xv6 файл user/initcode непосредственно не передаётся линковщику ядра. Его байты продублированы массивом:

    uchar initcode[] = { ... };

    в kernel/proc.c.

    То есть фактически в kernel/kernel массив попадает через:

    kernel/proc.c
    ↓
kernel/proc.o
    ↓
kernel/kernel

    Пользовательские программы не помещаются в секцииs ядра. Для них создаются отдельные исполняймые файлы.

    Общие пользовательские компоненты перечислены в:

    ULIB = $U/ulib.o $U/usys.o $U/printf.o $U/umalloc.o

    Это объектные файлы минимальной пользовательской библиотеки:

    user/ulib.o    → базовые функции строк и памяти
user/usys.o    → assembly-обёртки системных вызовов
user/printf.o  → пользовательский printf
user/umalloc.o → пользовательское выделение памяти

    Нужно различать одноимённые подсистемы:

    kernel/printf.c → вывод из ядра
user/printf.c   → вывод из пользовательских программ

kernel/kalloc.c → физические страницы ядра
user/umalloc.c  → память внутри пользовательской программы

    Обычная пользовательская программа собирается правилом:

    _%: %.o $(ULIB)
    $(LD) $(LDFLAGS) -T $U/user.ld -o $@ $^
    $(OBJDUMP) -S $@ > $*.asm
    $(OBJDUMP) -t $@ | sed '1,/SYMBOL TABLE/d; s/ .* / /; /^$$/d' > $*.sym

    Для цели:

    user/_cat

    Make получает:

    user/cat.o
user/ulib.o
user/usys.o
user/printf.o
user/umalloc.o

    и выполняет приблизительно:

    riscv64-linux-gnu-ld \
    -T user/user.ld \
    -o user/_cat \
    user/cat.o \
    user/ulib.o \
    user/usys.o \
    user/printf.o \
    user/umalloc.o

    Здесь:

    $@ → user/_cat
$^ → все зависимости
$* → user/cat

    Поэтому следующие команды создают:

    user/cat.asm
user/cat.sym

    Общая схема:

    user/cat.c
    ↓
user/cat.o
    +
ULIB
    +
user/user.ld
    ↓
user/_cat

    user/user.ld является линк-срипт пользовательской программы. Подробно он будет разобран вместе с exec() и пользовательским адресным пространством.

    Файл user/usys.o генерируется через:

    $U/usys.S: $U/usys.pl
    perl $U/usys.pl > $U/usys.S

$U/usys.o: $U/usys.S
    $(CC) $(CFLAGS) -c -o $U/usys.o $U/usys.S

    Получается:

    user/usys.pl
    ↓
user/usys.S
    ↓
user/usys.o
    ↓
ULIB
    ↓
каждая пользовательская программа

    usys.S содержит однотипные зависимости системных вызовов. Позднее путь будет выглядеть так:

    cat.c вызывает read()
        ↓
чтение зависимости из usys.o
        ↓
инструкция ecall
        ↓
переход в ядро

    Таким образом, уже на этапе сборки видно, что пользовательская программа не связывается непосредственно с функциями ядра. Она получает пользовательские зависимости, а фактическое обращение к ядру происходит только во время выполнения через специальный механизм системного вызова.

    Создание fs.img

    Собранные пользовательские программы перечислены в:

    UPROGS=\
    $U/_cat\
    $U/_echo\
    $U/_forktest\
    $U/_grep\
    $U/_init\
    $U/_kill\
    $U/_ln\
    $U/_ls\
    $U/_mkdir\
    $U/_rm\
    $U/_sh\
    $U/_stressfs\
    $U/_usertests\
    $U/_grind\
    $U/_wc\
    $U/_zombie\
    $U/_alloctest\
    $U/_reparenttest

    Программа не попадёт в начальную файловую систему только потому, что её исходник существует. Её исполняймый файл должен быть добавлен в UPROGS.

    Особенно важны:

    user/_init
user/_sh

    Они обеспечивают будущую цепочку:

    initcode
    ↓ exec("/init")
файл /init
    ↓
user/init.c
    ↓ exec("sh")
файл /sh
    ↓
user/sh.c

    Программа создания файловой системы собирается отдельно:

    mkfs/mkfs: mkfs/mkfs.c $K/fs.h $K/param.h
    gcc -Werror -Wall -I. -o mkfs/mkfs mkfs/mkfs.c

    Здесь используется обычный хостовый gcc, а не RISC-V cross-compiler.

    Следовательно:

    • адресов возврата

    • временных значений

    • аргументов, которые не поместились в регистры

    Привилегированные режимы RISC-V и начальная настройка ядра¶

    Уровень привилегий — это аппаратно контролируемый режим выполнения процессора, который определяет, какие операции текущему коду разрешены.

    Общая идея возникновения привелегий ясна - управления полномочиями пользовательских процессов и полный контроль за пк со стороны операционной системе коя единственная имеет все права. Контроль за выполнением дозволенных полномочий обеспечевивается при помощи просто вентиля "И" на аппаратном уровне. И при каждом вызове инструкции процессор в первую очередь проверят, а есть ли у него вообще право исполнять ее?

    И вроде нам известно о пользовательском режиме и о режиме ядра, но тут стоит вспомнить о букве m вначале некоторых имен спец регистров и команд, которая наконец приобритет смысл.

    В обычной конфигурации xv6-riscv используются ТРИ режима c соответствующей кодировкой: 

    U-mode (U - User) = 00
S-mode (S - Supervisor) = 01
M-mode (M - Machine) = 11

    M-mode (Machine Mode) — самый привилегированный режим RISC-V, предназначенный для низкоуровневого управления процессором и аппаратной платформой. После запуска QEMU, hart начинает выполнение именно в M-mode. Код, работающий в этом режиме, имеет доступ к machine-mode CSR и может настраивать такие механизмы, как делегирование исключений и прерываний, защиту физической памяти, таймеры и параметры последующего перехода в менее привилегированный режим. В обычной системе M-mode используется на начальном этапе запуска компьютера для настройки процессора и аппаратной платформы, после чего управление передаётся операционной системе, работающей в менее привилегированном режиме. В xv6 эту роль временно выполняет сама система. entry.S и start.c работают в M-mode, настраивают необходимое состояние процессора и после этого через mret переводят hart в S-mode, где уже выполняется основная часть ядра.

    Machine-mode CSR (Control and Status Registers) — это управляющие и статусные регистры RISC-V уровня Machine Mode, через которые наиболее привилегированный код получает доступ к низкоуровневому состоянию процессора и управляет его работой. Например, через такие регистры настраиваются режим привилегий, обработка исключений и прерываний, защита памяти и параметры возврата из M-mode.

    По назначению M-mode можно сравнить с уровнем, на котором работает BIOS/UEFI-подобный код, тк он используется для начальной настройки аппаратной платформы перед передачей управления операционной системе. Однако M-mode — это режим процессора, а BIOS/UEFI — программное обеспечение.

    S-mode (Supervisor Mode) — привилегированный режим RISC-V, предназначенный для работы ядра операционной системы. В xv6 именно в S-mode выполняется основная часть ядра, а именно управлением процессами, памятью, системными вызовами, прерываниями и устройствами.

    U-mode (User Mode) — наименее привилегированный режим RISC-V, предназначенный для выполнения пользовательских программ. Код в U-mode имеет ограниченные права и не может напрямую управлять ядром, аппаратурой или защищённой памятью, для этого он обращается к ядру через системные вызовы.

    Замечание

    Стоит отметить, что схема M-mode → S-mode → U-mode характерна именно для RISC-V и представляет собой достаточно простую и наглядную модель разделения привилегий. В других архитектурах количество и назначение уровней могут отличаться, однако общий принцип сохраняется: пользовательский код выполняется с ограниченными правами, ядро — с расширенными, а при необходимости существуют дополнительные более привилегированные уровни для управления самой платформой, firmware или виртуализацией.

    SBI (Supervisor Binary Interface) — стандартизированный для RISC-V программный интерфейс между ядром операционной системы, работающим в S-mode, и низкоуровневой firmware, работающей в M-mode. Через вызовы SBI ядро может запрашивать привилегированные операции, которые оно не вправе выполнять самостоятельно: управление hart, межпроцессорные прерывания, перезагрузку системы и некоторые функции таймера. SBI является спецификацией интерфейса, а OpenSBI — одной из его реализаций.

    OpenSBI (Open Supervisor Binary Interface) — открытая реализация стандарта SBI для RISC-V, представляющая собой низкоуровневую системную firmware, работающую в M-mode между аппаратной платформой и ядром операционной системы. OpenSBI выполняет первоначальную настройку процессора и платформы, передаёт управление ядру в S-mode и предоставляет ему стандартный интерфейс для выполнения операций, требующих привилегий M-mode.

    Что изменилось бы при использовании firmware

    Параметр -bios none в Makefile не отключает сам M-mode — M-mode является аппаратным режимом RISC-V и существует независимо от наличия firmware. Этот параметр означает лишь, что QEMU не загружает отдельную программу, которая работала бы в M-mode до запуска ядра.

    Если вместо -bios none использовать -bios default, QEMU обычно загрузит OpenSBI. Тогда после запуска hart сначала начнёт выполнять OpenSBI в M-mode. OpenSBI настроит наиболее привилегированное состояние платформы: защиту физической памяти, машинные прерывания, состояние hart и условия запуска операционной системы. После этого OpenSBI передаст управление ядру уже в S-mode.

    При этом OpenSBI не обязательно полностью прекращает существование после запуска ядра. Оно остаётся промежуточным слоем между S-mode и аппаратурой. Если ядру потребуется операция, доступная только в M-mode, оно сможет обратиться к OpenSBI через интерфейс SBI

    Таким образом, существуют две схемы загрузки:

    Без отдельной firmware:

    QEMU → xv6 entry.S в M-mode → xv6 start.c → mret → xv6 main.c в S-mode

    С OpenSBI:

    QEMU → OpenSBI в M-mode → начальная настройка платформы → ядро в S-mode

    Текущую xv6 нельзя запустить через OpenSBI простой заменой -bios none на -bios default. Её entry.S и start.c предполагают, что ядро получает управление в M-mode: они читают mhartid, изменяют machine-mode CSR, настраивают PMP и выполняют mret. Если OpenSBI передаст управление уже в S-mode, такие операции окажутся запрещёнными. Для этой схемы начальный код xv6 пришлось бы изменить: получать номер hart от firmware, убрать самостоятельную настройку M-mode и использовать SBI для необходимых машинных операций.

    medeleg Machine Exception Delegation Register Определяет, какие исключения, возникшие на менее привилегированных уровнях, разрешено обрабатывать непосредственно в S-mode. kernel/start.c, kernel/riscv.h
    mideleg Machine Interrupt Delegation Register Определяет, какие прерывания разрешено передавать для обработки непосредственно в S-mode. kernel/start.c, kernel/riscv.h
    mie Machine Interrupt Enable Register Разрешает отдельные типы прерываний M-mode kernel/start.c, kernel/riscv.h
    mtvec Machine Trap-Vector Base Address Register Хранит адрес обработчика trap в M-mode. xv6 записывает в него адрес timervec. kernel/start.c, kernel/riscv.h
    mscratch Machine Scratch Register Предоставляет временное хранилище обработчику M-mode. xv6 хранит в нём указатель на timer_scratch текущего hart. kernel/start.c, kernel/kernelvec.S, kernel/riscv.h
    pmpaddr0 Physical Memory Protection Address Register 0 Задаёт адресную границу первой области защиты физической памяти. xv6 устанавливает границу, охватывающую используемую физическую память. kernel/start.c, kernel/riscv.h
    pmpcfg0 Physical Memory Protection Configuration Register 0 Определяет режим и права первой области PMP. xv6 разрешает S-mode чтение, запись и исполнение во всей заданной области. kernel/start.c, kernel/riscv.h

    Битовая организация CSR-регистров¶

    В отличие от обычных регистров общего назначения (x0–x31), содержимое которых в общем случае рассматривается процессором просто как некоторое XLEN-битное значение, CSR-регистры имеют заранее определённый архитектурой формат.

    Например, значение в обычном регистре:

    x5 = 10110100...

    само по себе не означает, что:

    bit 3 — режим процессора;
bit 7 — разрешение прерываний;
bits 11:12 — уровень привилегий.

    Назначение значения x5 определяется программой.

    У CSR ситуация другая. Спецификация RISC-V заранее определяет, что конкретные позиции регистра имеют конкретное назначение.

    Например, для mstatus:

    bit 3      → MIE
bit 7      → MPIE
bits 11:12 → MPP
bit 17     → MPRV
bit 18     → SUM
bit 19     → MXR
...

    Таким образом, CSR можно рассматривать как битовую структуру аппаратного состояния:

    64-битный CSR

63                                               0
┌──────┬───────┬─────┬──────────┬─────┬─────────┐
│ поле │ поле  │ ... │   поле   │ ... │  поле   │
└──────┴───────┴─────┴──────────┴─────┴─────────┘

    При этом утверждение «каждый бит CSR обязательно чем-то занят» неверно. Архитектура может оставить некоторые позиции зарезервированными либо определить для них специальные правила чтения и записи.

    В спецификации встречаются, в частности, следующие обозначения:

    WPRI — Reserved Writes Preserve Values, Reads Ignore Values

WARL — Write Any, Read Legal

WLRL — Write/Read Only Legal Values

    То есть CSR представляет собой не просто число, а описанный архитектурой набор битовых полей со своими правилами поведения. Конкретная реализация процессора также может не поддерживать некоторые опциональные поля или расширения.

    Для понимания start.c xv6 особенно важны три таких регистра:

    mstatus — состояние и управление M-mode;

medeleg — делегирование исключений из M-mode в S-mode;

mideleg — делегирование прерываний из M-mode в S-mode.

    mstatus (Machine Status Register) — основной CSR состояния M-mode. В RV64 его ширина равна MXLEN, то есть в используемой xv6 конфигурации это 64 бита.

    Он не хранит какое-либо одно значение. Его 64 бита разбиты на множество независимых полей, связанных с:

    прерываниями;
предыдущим privilege mode;
возвратом через mret/sret;
виртуальной памятью;
доступом к памяти;
состоянием архитектурных расширений;
разрядностью нижних privilege modes;
endianness;
дополнительными расширениями ISA.

    RISC-V определяет mstatus как регистр, который отслеживает и управляет текущим операционным состоянием hart.

    Для базовой RV64-системы с M/S/U его основную структуру удобно представить так:

    63                                                                  0

63      SD

38      MBE
37      SBE
36      зарезервировано / WPRI

35:34   SXL
33:32   UXL

31:23   в базовой конфигурации WPRI
22      TSR
21      TW
20      TVM
19      MXR
18      SUM
17      MPRV

16:15   XS
14:13   FS
12:11   MPP
10:9    VS

8       SPP
7       MPIE
6       UBE
5       SPIE
4       WPRI
3       MIE
2       WPRI
1       SIE
0       WPRI

    Некоторые современные расширения RISC-V используют дополнительные позиции mstatus. Например Hypervisor extension добавляет GVA и MPV, а другие расширения способны добавлять дополнительные поля. Поэтому свободные/WPRI-позиции нельзя воспринимать как навсегда предназначенные для нуля.

    SIE = Supervisor Interrupt Enable

    Глобальный флаг разрешения supervisor-прерываний.

    SIE = 0
    supervisor interrupts глобально запрещены

SIE = 1
    supervisor interrupts могут быть приняты,
    если выполнены остальные условия

    Это именно глобальное разрешение для соответствующего privilege level. Отдельные типы supervisor interrupts дополнительно контролируются sie.

    MIE = Machine Interrupt Enable

    Аналогичный глобальный переключатель для M-mode:

    MIE = 0
    machine interrupts глобально запрещены

MIE = 1
    machine interrupts могут приниматься

    Это не означает, что любой interrupt автоматически произойдёт: должны также выполняться условия, связанные с mie, mip, mideleg и текущим privilege mode.

    SPIE = Supervisor Previous Interrupt Enable

    Хранит предыдущее значение SIE.

    При входе в supervisor trap процессору необходимо временно изменить состояние разрешения прерываний, но сохранить старое состояние для последующего sret.

    Концептуально:

    trap → S-mode

SPIE ← SIE
SIE  ← 0

    При sret сохранённое состояние используется для восстановления interrupt state.

    UBE = User-mode Big Endian

    Определяет endianness явных обращений к памяти из U-mode:

    UBE = 0 → little-endian
UBE = 1 → big-endian

    Instruction fetch при этом остаётся little-endian.

    MPIE = Machine Previous Interrupt Enable

    То же назначение, что SPIE, только для M-mode.

    При входе в machine trap:

    MPIE ← MIE
MIE  ← 0

    А при mret сохранённое значение участвует в восстановлении состояния.

    SPP = Supervisor Previous Privilege

    Хранит privilege mode, из которого был выполнен вход в S-mode.

    Поскольку ниже S-mode существует только U-mode, достаточно одного бита:

    SPP = 0 → предыдущий режим U
SPP = 1 → предыдущий режим S

    SRET использует это поле при возврате.

    VS = Vector extension state

    Содержит состояние vector-контекста, если соответствующее расширение реализовано.

    Типичная кодировка:

    00 → Off
01 → Initial
10 → Clean
11 → Dirty

    Это позволяет привилегированному коду понимать, требуется ли сохранять vector state при переключении контекста.

    MPP = Machine Previous Privilege

    Одно из важнейших полей для xv6.

    Оно определяет privilege mode, который считается предыдущим для M-mode и в который mret должен вернуть выполнение.

    Кодировки:

    00 → U-mode
01 → S-mode
11 → M-mode

    Именно поэтому поле занимает два бита.

    В xv6 определено:

    #define MSTATUS_MPP_MASK (3L << 11)
#define MSTATUS_MPP_M    (3L << 11)
#define MSTATUS_MPP_S    (1L << 11)
#define MSTATUS_MPP_U    (0L << 11)

    Число:

    3 = 0b11

    представляет двухбитную маску.

    Сдвиг:

    3L << 11

    перемещает её в позиции [12:11]:

    bit:       12 11
            ↓ ↓
           [1 1]

    Поэтому:

    x &= ~MSTATUS_MPP_MASK;

    очищает только MPP, после чего:

    x |= MSTATUS_MPP_S;

    записывает:

    MPP = 01 = Supervisor

    При этом hart ещё остаётся в M-mode. Значение MPP будет использовано только при последующем mret. RISC-V определяет, что xRET восстанавливает privilege mode из соответствующего xPP-поля.

    FS = Floating-point Status

    Отражает состояние floating-point контекста:

    00 → Off
01 → Initial
10 → Clean
11 → Dirty

    Если состояние Dirty, ОС понимает, что floating-point registers были изменены и при необходимости должны быть сохранены.

    XS = Extension Status

    Сводное состояние некоторых дополнительных расширений.

    Как и FS/VS, позволяет ОС определить необходимость сохранения дополнительного architectural state.

    MPRV = Modify PRiVilege

    Изменяет эффективный privilege mode для load/store.

    Если:

    MPRV = 0

    доступ к памяти производится с обычными правами текущего privilege mode.

    Если:

    MPRV = 1

    явные load/store из M-mode проверяются так, как если бы выполнялись с privilege mode, указанным в MPP.

    Например:

    current mode = M
MPP          = S
MPRV         = 1

    тогда:

    инструкции выполняются в M-mode,
но load/store проверяются как S-mode.

    Instruction fetch от MPRV не зависит.

    SUM = permit Supervisor User Memory access

    Управляет доступом S-mode к страницам, помеченным как пользовательские (PTE.U = 1).

    SUM = 0
    S-mode load/store в U-страницу вызывает fault

SUM = 1
    S-mode может выполнять load/store в U-страницы

    Этот бит имеет смысл при включённой страничной виртуальной памяти.

    MXR = Make eXecutable Readable

    Изменяет трактовку прав страниц для load.

    При:

    MXR = 0

    читать можно страницу с:

    R = 1

    При:

    MXR = 1

    для чтения достаточно:

    R = 1
или
X = 1

    То есть execute-only page может рассматриваться как readable для load.

    TVM = Trap Virtual Memory

    Позволяет M-mode ограничить некоторые операции S-mode, связанные с управлением виртуальной памятью.

    При установленном TVM определённые supervisor-операции с механизмом виртуальной памяти приводят к trap вместо обычного выполнения.

    Таким образом M-mode способен сохранить контроль над частью virtual-memory machinery.

    TW = Timeout Wait

    Связан с поведением инструкции:

    wfi

    WFI — Wait For Interrupt.

    Поле позволяет M-mode контролировать использование этой инструкции менее привилегированным кодом.

    TSR = Trap SRET

    Позволяет M-mode ограничивать использование sret в S-mode.

    При соответствующей настройке попытка S-mode выполнить:

    sret

    приводит к исключению.

    UXL = User XLEN

    Определяет эффективную разрядность U-mode.

    Для RV64 обычно:

    UXL = 10₂ → 64 bits

    SXL = Supervisor XLEN

    Аналогично задаёт effective XLEN для S-mode.

    Для xv6-riscv:

    SXLEN = 64

    Поля SXL и UXL являются WARL.

    SBE = Supervisor Big Endian

    0 → little-endian
1 → big-endian

    для соответствующих S-mode memory accesses.

    MBE = Machine Big Endian

    То же самое для M-mode.

    SD = State Dirty

    Сводный read-only бит.

    Он устанавливается, если один из отслеживаемых extension-state (FS, VS, XS) находится в состоянии Dirty.

    Условно:

    SD =
    FS == Dirty
    OR VS == Dirty
    OR XS == Dirty

    Это позволяет ОС быстро определить, существует ли дополнительный изменённый контекст, который может потребоваться сохранить.

    Таким образом mstatus можно воспринимать как большую аппаратную структуру:

    mstatus

┌────────────────────────────────────────────┐
│ состояние privilege transition            │
│   MPP, SPP                                 │
├────────────────────────────────────────────┤
│ состояние interrupts                      │
│   MIE, MPIE, SIE, SPIE                    │
├────────────────────────────────────────────┤
│ правила memory access                     │
│   MPRV, SUM, MXR                          │
├────────────────────────────────────────────┤
│ управление S-mode                         │
│   TVM, TW, TSR                            │
├────────────────────────────────────────────┤
│ extension state                           │
│   FS, VS, XS, SD                          │
├────────────────────────────────────────────┤
│ архитектурная конфигурация                │
│   SXL, UXL, MBE, SBE, UBE                 │
└────────────────────────────────────────────┘

    medeleg (Machine Exception Delegation Register) определяет, какие синхронные исключения, возникшие в менее привилегированном режиме, разрешено обрабатывать непосредственно в S-mode вместо M-mode.

    На RV64 medeleg является 64-битным CSR.

    Принцип его устройства отличается от mstatus.

    В mstatus разные группы битов образуют разные поля:

    MPP
MIE
SUM
MXR
...

    А medeleg фактически представляет собой битовую таблицу исключений:

    bit N ↔ exception code N

    Номер бита совпадает с кодом соответствующего exception в mcause.

    То есть:

    medeleg[N] = 0
    exception N не делегирован S-mode

medeleg[N] = 1
    exception N делегирован S-mode,
    если данный exception вообще допускает делегирование

    Основное распределение младших битов:

    bit 0
Instruction address misaligned

bit 1
Instruction access fault

bit 2
Illegal instruction

bit 3
Breakpoint

bit 4
Load address misaligned

bit 5
Load access fault

bit 6
Store/AMO address misaligned

bit 7
Store/AMO access fault

bit 8
Environment call from U-mode

bit 9
Environment call from S-mode

bit 10
Reserved

bit 11
Environment call from M-mode

bit 12
Instruction page fault

bit 13
Load page fault

bit 19

    Эти номера соответствуют стандартным exception codes, возвращаемым через mcause.

    Особенно важен для xv6:

    medeleg[8]

    Поскольку:

    exception code 8
=
Environment call from U-mode

    Если:

    medeleg[8] = 1

    то пользовательский:

    ecall

    может привести непосредственно к supervisor trap:

    U-mode
   │
   │ ecall
   ▼
S-mode

    вместо передачи события в M-mode. RISC-V прямо приводит bit 8 как пример делегирования user-mode environment call.

    Важно понимать, что делегирование действует не вниз из M-mode во время исполнения M-mode-кода.

    Если:

    medeleg[2] = 1

    и Illegal instruction возникает в U-mode или S-mode, trap может быть обработан S-mode.

    Но если illegal instruction выполняется самим M-mode, процессор не сделает:

    M → S

    Trap никогда не переводит выполнение из более привилегированного режима в менее привилегированный. В таком случае он останется M-mode trap.

    Ещё одно важное ограничение:

    medeleg[11]

    соответствует:

    Environment call from M-mode

    и является read-only zero, поскольку такой exception не может возникнуть в менее привилегированном режиме и потому не имеет смысла делегировать S-mode. В актуальной спецификации также medeleg[16], соответствующий double trap, не делегируется.

    В xv6 используется:

    w_medeleg(0xffff);

    Значение:

    0xffff =
1111 1111 1111 1111₂

    означает попытку установить:

    medeleg[15:0] = 1

    То есть xv6 просит аппаратную реализацию делегировать S-mode все поддерживаемые исключения из младших шестнадцати категорий.

    Однако запись:

    w_medeleg(0xffff);

    не гарантирует, что после записи все 16 бит действительно станут единицами.

    Реализация может поддерживать только некоторый набор делегируемых traps. Спецификация рекомендует определять реально поддерживаемые биты посредством записи единиц и последующего чтения регистра обратно.

    Если exception делегирован в S-mode, процессор заполняет уже supervisor trap-state:

    scause
sepc
stval

и поля:
SPP
SPIE
SIE

    а соответствующий machine trap-state:

    mcause
mepc
mtval
MPP
MPIE

    при этом не обновляется.

    То есть:

    exception
    │
    ▼
medeleg
    │
    ├── bit = 0 ──→ M-mode trap machinery
    │
    └── bit = 1 ──→ S-mode trap machinery

    На RV64 его ширина равна MXLEN, то есть 64 бита.

    Как и medeleg, это в основном битовая таблица:

    mideleg[N]
    ↕
interrupt cause N

    Расположение битов соответствует расположению interrupt causes в mip/mie.

    Стандартные interrupt cause numbers определены архитектурой, а позиции 16+ оставлены для platform-specific interrupt sources.

    Особенно важны для S-mode три бита:

    mideleg[1]
    Supervisor Software Interrupt

mideleg[5]
    Supervisor Timer Interrupt

mideleg[9]
    Supervisor External Interrupt

    Например:

    mideleg[5] = 1

    означает:

    Supervisor Timer Interrupt
делегирован в S-mode

    Спецификация непосредственно приводит mideleg[5] как пример делегирования supervisor timer interrupt.

    Смысл можно представить так:

    interrupt i возник
       │
       ▼
mideleg[i]
       │
       ├── 0 → interrupt относится к M-mode
       │
       └── 1 → interrupt делегирован S-mode

    При этом mideleg не разрешает обработку interrupt сам по себе.

    Он отвечает только на вопрос:

    КАКОМУ privilege level принадлежит этот interrupt?

    После делегирования interrupt становится видимым supervisor-механизмам sip и sie. Спецификация прямо определяет, что делегированный через mideleg interrupt становится видимым в sip и может маскироваться соответствующим битом sie.

    Отсюда возникает полная цепочка:

    interrupt возник
        │
        ▼
     mideleg
        │
        │ делегирован S-mode?
        ▼
       sip
        │
        │ pending?
        ▼
       sie
        │
        │ данный тип разрешён?
        ▼
sstatus.SIE
        │
        │ supervisor interrupts
        │ глобально разрешены?
        ▼
    S-mode trap

    Именно поэтому в xv6 рядом находятся:

    w_mideleg(0xffff);

w_sie(r_sie() | SIE_SEIE | SIE_STIE | SIE_SSIE);

    Первая операция:

    w_mideleg(0xffff);

    говорит:

    попытаться делегировать S-mode
поддерживаемые interrupt classes

    А:

    w_sie(...)

    уже говорит:

    в S-mode разрешить конкретные
типы supervisor interrupts

    Это принципиально разные уровни управления:

    mideleg
    маршрутизация между M и S

sie
    индивидуальное разрешение
    interrupt в S-mode

sstatus.SIE
    глобальное разрешение
    supervisor interrupts

    Разбор start.c¶

    start.c — это не основное ядро, а короткий переходный код. Каждый hart выполняет его в M-mode после entry.S. Файл подготавливает процессор к работе ядра в S-mode. Это первый С код.

    В самом начале импортируются 4 заголовочных файла

    • memlayout.h → физические адреса устройств QEMU, включая CLINT

    • param.h → NCPU и другие ограничения xv6

    • riscv.h → CSR, флаги CSR и функции для их чтения/записи

    • types.h → uint64 и другие целочисленные типы

    дальше идет объявление 

    void main();
void timerinit();

    Это объявления двух функций, которые понадобятся ниже. Они сообщают компилятору имена функций и тип возвращаемого ими значения.

    main() реализована в kernel/main.c. Это основная C-функция ядра, в которую start() передаст управление после завершения настройки M-mode.

    timerinit() реализована ниже в этом же файле и отвечает за первоначальную настройку таймера каждого hart.

    Далее находится уже рассмотренный при разборе entry.S массив:

    __attribute__((aligned(16))) char stack0[4096 * NCPU];

    Следующий глобальный массив предназначен уже не для стека, а для обработчика машинного таймера:

    uint64 timer_scratch[NCPU][5];

    Для каждого возможного hart выделяется по пять 64-битных значений:

    timer_scratch[0] → служебные данные hart 0
timer_scratch[1] → служебные данные hart 1
timer_scratch[2] → служебные данные hart 2
...

    Одна строка позднее будет использоваться следующим образом:

    scratch[0] → временное сохранение регистра a1
scratch[1] → временное сохранение регистра a2
scratch[2] → временное сохранение регистра a3
scratch[3] → адрес таймера mtimecmp текущего hart
scratch[4] → интервал между таймерными прерываниями

    Как и stack0, массив не имеет явного начального значения, поэтому размещается в секции .bss.

    Далее объявляется внешний символ:

    extern void timervec();

    timervec — ассемблерный обработчик машинного таймерного прерывания, реализованный в kernel/kernelvec.S.

    Ключевое слово extern означает, что реализация символа находится в другом объектном файле:

    start.o
└── содержит обращение к timervec

kernelvec.o
└── содержит реализацию timervec

start.o + kernelvec.o
          ↓ linker
     kernel/kernel

    Само объявление extern не создаёт функцию и не выделяет для неё память. Оно только позволяет компилятору сформировать обращение к символу, который позднее найдёт линкер.

    После глобальных объявлений начинается сама функция:

    void
start()
{

    На входе в неё каждый hart уже имеет собственный стек, но всё ещё работает в M-mode:

    текущий режим = M-mode
PC = адрес start
sp = вершина стека текущего hart
ra = адрес метки spin из entry.S

    Сначала start() подготавливает будущий переход в S-mode:

    unsigned long x = r_mstatus();
x &= ~MSTATUS_MPP_MASK;
x |= MSTATUS_MPP_S;
w_mstatus(x);

    Функция r_mstatus() читает текущее значение CSR mstatus:

    unsigned long x = r_mstatus();

    В riscv.h она реализована через инструкцию csrr:

    static inline uint64
r_mstatus()
{
  uint64 x;
  asm volatile("csrr %0, mstatus" : "=r" (x));
  return x;
}

    Нас интересует двухбитное поле MPP — Machine Previous Privilege. Инструкция mret использует его, чтобы определить режим продолжения выполнения:

    MPP = 00 → U-mode
MPP = 01 → S-mode
MPP = 11 → M-mode

    Сначала старое значение MPP очищается:

    x &= ~MSTATUS_MPP_MASK;

    В riscv.h маска определена так:

    #define MSTATUS_MPP_MASK (3L << 11)

    Число 3 в двоичной системе равно 11. После сдвига на 11 позиций маска указывает на два бита поля MPP. Операция ~ инвертирует маску, а побитовое AND очищает выбранные биты, не изменяя остальные части mstatus.

    После этого устанавливается значение S-mode:

    x |= MSTATUS_MPP_S;

    где:

    #define MSTATUS_MPP_S (1L << 11)

    И изменённое значение записывается обратно в CSR:

    w_mstatus(x);

    В результате:

    mstatus.MPP = S-mode

    Несмотря на название Machine Previous Privilege, при начальной загрузке xv6 вручную использует MPP как настройку будущего перехода. Эта операция пока не меняет текущий режим: start() продолжает выполняться в M-mode.

    Следом определяется адрес, по которому нужно продолжить выполнение:

    w_mepc((uint64)main);

    Имя функции main преобразуется в её числовой адрес и записывается в mepc:

    mepc = адрес main

    Теперь для будущей инструкции mret подготовлены две независимые настройки:

    mstatus.MPP → в каком режиме продолжить выполнение
mepc → по какому адресу продолжить выполнение

    Переход всё ещё не произошёл. Он будет выполнен только в конце start().

    До создания таблиц страниц виртуальная память отключается:

    w_satp(0);

    CSR satp управляет трансляцией виртуальных адресов S-mode. Запись нуля устанавливает режим Bare, в котором таблицы страниц не используются:

    satp = 0
    ↓
режим Bare
    ↓
трансляция Sv39 выключена

    На этом этапе ядро может работать без трансляции, поскольку оно слинковано для адреса 0x80000000 и QEMU загрузил его по этому же физическому адресу.

    Виртуальная память будет включена позднее в main():

    kvminit();      // создать таблицу страниц ядра
kvminithart();  // установить её в satp и включить Sv39

    Далее xv6 передаёт основному ядру обработку исключений и прерываний:

    w_medeleg(0xffff);
w_mideleg(0xffff);

    Исключение или exception, — синхронное событие, вызванное выполняемой инструкцией. К исключениям относятся системный вызов ecall, недопустимая инструкция и ошибка доступа к странице.

    Прерывание или interrupt, — асинхронное событие, возникающее независимо от текущей инструкции. Например, таймер может сработать, а устройство — сообщить о завершении операции.

    Trap — общее название передачи управления специальному обработчику из-за исключения или прерывания:

    trap = exception или interrupt

    medeleg — Machine Exception Delegation. Он определяет, какие исключения можно передавать для обработки в S-mode:

    w_medeleg(0xffff);

    mideleg — Machine Interrupt Delegation. Он аналогично управляет передачей прерываний:

    w_mideleg(0xffff);

    Значение 0xffff пытается установить первые шестнадцать бит каждого регистра. Процессор сохранит только те биты, которые поддерживаются и могут быть делегированы.

    В результате поддерживаемые события, возникшие в U-mode или S-mode, сможет обрабатывать основное ядро:

    trap возникает в U/S-mode
        ↓
соответствующий бит делегирования установлен
        ↓
управление получает обработчик S-mode

    Если событие возникает непосредственно в M-mode, оно не передаётся менее привилегированному S-mode. Поэтому машинное таймерное прерывание в этой версии xv6 сначала принимает небольшой обработчик timervec, работающий в M-mode.

    Следующая строка разрешает три категории прерываний S-mode:

    w_sie(r_sie() | SIE_SEIE | SIE_STIE | SIE_SSIE);

    Сначала r_sie() читает текущее значение CSR sie. Затем побитовая операция OR устанавливает флаги:

    SEIE → Supervisor External Interrupt Enable (внешние прерывания устройств)
STIE → Supervisor Timer Interrupt Enable (таймерное прерывание уровня Supervisor)
SSIE → Supervisor Software Interrupt Enable (программное прерывание уровня Supervisor)

    В нашей версии xv6 машинный обработчик таймера уведомляет S-mode через программное прерывание SSIE.

    При этом sie разрешает только отдельные категории. Глобальный приём S-mode-прерываний управляется другим флагом:

    sie → какие виды прерываний разрешены
sstatus.SIE → разрешён ли их приём в целом

    Флаг sstatus.SIE будет включён позднее функцией intr_on(), когда ядро подготовит обработчики trap.

    Важно различать

    medeleg (Machine Exception Delegation Register) определяет, какие исключения должны обрабатываться в S-mode, а не в M-mode.

    mideleg (Machine Interrupt Delegation Register) выполняет ту же роль для прерываний.

    sie (Supervisor Interrupt Enable Register) не определяет, куда передавать прерывание. Он задаёт, какие типы supervisor-прерываний вообще разрешено принимать в S-mode.

    В xv6 используется строка:

    w_sie(r_sie() | SIE_SEIE | SIE_STIE | SIE_SSIE);

    Она:

    1. считывает текущее значение sie;
    2. устанавливает необходимые биты;
    3. записывает новое значение обратно.

    Основные используемые биты:

    bit 1  — SSIE — Supervisor Software Interrupt Enable
bit 5  — STIE — Supervisor Timer Interrupt Enable
bit 9  — SEIE — Supervisor External Interrupt Enable

    Их назначение:

    SSIE = 1 → разрешены software interrupts
STIE = 1 → разрешены timer interrupts
SEIE = 1 → разрешены external interrupts

    Таким образом, обработка supervisor-прерывания требует нескольких условий:

    interrupt возник
↓
mideleg
↓
делегирован ли он в S-mode?
↓
sie
↓
разрешён ли конкретный тип interrupt?
↓
sstatus.SIE
↓
разрешены ли supervisor interrupts глобально?
↓
trap в S-mode

    Следующие две строки настраивают Physical Memory Protection:

    w_pmpaddr0(0x3fffffffffffffull);
w_pmpcfg0(0xf);

    PMP или Physical Memory Protection, — аппаратный механизм, позволяющий M-mode определять доступ менее привилегированных режимов к физической памяти.

    Здесь используются два CSR:

    pmpaddr0 → адресная граница области
pmpcfg0 → режим области и разрешённые операции

    Сначала задаётся очень большая верхняя граница:

    w_pmpaddr0(0x3fffffffffffffull);

    Затем настраиваются права области:

    w_pmpcfg0(0xf);

    Младшие биты значения 0xf означают:

    R = 1 → чтение разрешено
W = 1 → запись разрешена
X = 1 → исполнение разрешено
A = 01 → режим TOR

    TOR или Top Of Range, означает, что pmpaddr0 задаёт верхнюю границу области. Для первой записи PMP нижней границей является ноль.

    В результате S-mode получает возможность читать, изменять и исполнять код во всей необходимой xv6 физической памяти.

    Это не означает, что пользовательские программы также получат доступ ко всей памяти. В дальнейшем таблицы страниц введут дополнительные ограничения:

    PMP
└── определяет, к какой физической памяти в принципе
    могут обращаться менее привилегированные режимы

таблицы страниц
└── определяют, какие виртуальные страницы доступны
    конкретному коду и с какими правами

    После подготовки перехода и памяти вызывается:

    timerinit();

    timerinit() настраивает периодический таймер отдельно для текущего hart. Позднее его прерывания позволят ядру периодически получать управление и при необходимости переключать процессы:

    процесс выполняется
        ↓
срабатывает таймер
        ↓
ядро получает управление
        ↓
может быть вызван yield()
        ↓
планировщик выбирает другой процесс

    Функция начинается с чтения номера текущего hart:

    int id = r_mhartid();

    Каждому hart соответствует отдельный регистр сравнения таймера и отдельная строка timer_scratch.

    Затем определяется интервал между прерываниями:

    int interval = 1000000;

    Исходный комментарий называет это количество циклами, но точнее говорить о тиках аппаратного счётчика времени. В используемой QEMU-платформе значение приблизительно соответствует одной десятой секунды.

    Момент первого прерывания устанавливается строкой:

    *(uint64 *)CLINT_MTIMECMP(id) =
    *(uint64 *)CLINT_MTIME + interval;

    CLINT или Core-Local Interruptor, — блок локальных прерываний hart. В нашей версии QEMU через него доступен машинный таймер.

    В memlayout.h определены адреса двух его регистров:

    #define CLINT 0x2000000L
#define CLINT_MTIMECMP(hartid) (CLINT + 0x4000 + 8 * (hartid))
#define CLINT_MTIME (CLINT + 0xBFF8)

    mtime — непрерывно увеличивающийся счётчик времени:

    CLINT_MTIME → текущее значение времени

    mtimecmp — отдельный регистр сравнения для каждого hart:

    CLINT_MTIMECMP(id) → момент следующего прерывания hart id

    Эти регистры являются memory-mapped registers: устройству назначены физические адреса, поэтому процессор читает и изменяет его состояние обычными обращениями к памяти.

    Выражение:

    *(uint64 *)CLINT_MTIME

    означает:

    1. Взять числовой адрес CLINT_MTIME.
    2. Рассматривать его как адрес 64-битного значения.
    3. Прочитать значение по этому адресу.

    Вся строка устанавливает:

    mtimecmp[id] = mtime + interval

    Когда выполняется условие:

    mtime >= mtimecmp[id]

    у соответствующего hart появляется ожидающее машинное таймерное прерывание.

    Далее выбирается строка служебной памяти текущего hart:

    uint64 *scratch = &timer_scratch[id][0];

    Например:

    hart 0 → scratch = &timer_scratch[0][0]
hart 1 → scratch = &timer_scratch[1][0]
hart 2 → scratch = &timer_scratch[2][0]

    В четвёртый элемент записывается адрес индивидуального mtimecmp:

    scratch[3] = CLINT_MTIMECMP(id);

    Это именно адрес регистра, а не его текущее значение:

    scratch[3] = адрес mtimecmp[id]

    В пятый элемент записывается интервал:

    scratch[4] = interval;

    Позднее timervec использует эти значения, чтобы назначить следующий тик:

    получить адрес mtimecmp из scratch[3]
        ↓
получить interval из scratch[4]
        ↓
mtimecmp += interval

    Первые три элемента понадобятся обработчику для временного сохранения регистров a1, a2 и a3.

    Указатель на выбранную строку записывается в CSR mscratch:

    w_mscratch((uint64)scratch);

    Поскольку у каждого hart собственный mscratch, получается:

    hart 0: mscratch → timer_scratch[0]
hart 1: mscratch → timer_scratch[1]
hart 2: mscratch → timer_scratch[2]

    При возникновении прерывания обработчик сможет быстро получить этот указатель, не вычисляя номер hart заново.

    Адрес самого обработчика записывается в mtvec:

    w_mtvec((uint64)timervec);

    После этого машинный trap направляется по адресу timervec:

    возникает machine timer interrupt
        ↓
hart входит в M-mode
        ↓
PC получает значение mtvec
        ↓
начинается timervec

    В конце timerinit() разрешается машинное таймерное прерывание.

    Сначала устанавливается общий флаг M-mode-прерываний:

    w_mstatus(r_mstatus() | MSTATUS_MIE);

    То есть:

    mstatus.MIE = 1

    Затем разрешается конкретно машинный таймер:

    w_mie(r_mie() | MIE_MTIE);

    То есть:

    mie.MTIE = 1

    Разница между этими настройками:

    mstatus.MIE → общий переключатель машинных прерываний
mie.MTIE    → разрешение машинного таймера

    После завершения timerinit() таймер работает по следующей схеме:

    mtime увеличивается
        ↓
mtime достигает mtimecmp[id]
        ↓
возникает machine timer interrupt
        ↓
управление получает timervec в M-mode
        ↓
timervec назначает следующий тик
        ↓
timervec создаёт программное прерывание S-mode
        ↓
основное ядро xv6 получает управление

    Подробный разбор timervec пока отложим до kernelvec.S и общей системы trap. На текущем этапе достаточно понимать его контракт: он превращает машинное таймерное прерывание в программное прерывание для основного ядра.

    После возвращения из timerinit() номер текущего hart сохраняется в регистре tp:

    int id = r_mhartid();
w_tp(id);

    r_mhartid() читает номер hart из machine-mode CSR:

    id = mhartid

    w_tp(id) копирует его в обычный регистр tp:

    tp = id

    tp, или thread pointer, — обычный регистр RISC-V x4, а не CSR. xv6 использует его для хранения номера hart во время работы ядра.

    Это необходимо прежде всего потому, что после перехода в S-mode ядро не сможет читать machine-mode CSR mhartid. Регистр tp, напротив, доступен в S-mode.

    Позднее функция cpuid() будет получать номер hart именно из tp:

    int
cpuid()
{
  int id = r_tp();
  return id;
}

    Следовательно:

    cpuid() → прочитать номер текущего hart из tp

    Нет оснований называть чтение mhartid обязательно дорогой операцией. Главная причина копирования — доступность tp после перехода в S-mode и удобство его постоянного использования ядром.

    После всех приготовлений выполняется последняя инструкция start():

    asm volatile("mret");

    asm вставляет ассемблерную инструкцию непосредственно в C-код. Слово volatile запрещает компилятору удалить или произвольно переставить эту вставку.

    К этому моменту состояние hart подготовлено:

    mstatus.MPP = S-mode
mepc        = адрес main
satp        = 0, трансляция выключена
sp          = стек текущего hart
tp          = номер текущего hart
PMP         = S-mode разрешена физическая память
mtvec       = адрес timervec
таймер      = настроен

    Основные действия mret:

    текущий режим ← mstatus.MPP
PC            ← mepc

    В нашем случае:

    текущий режим ← S-mode
PC            ← адрес main

    После этого hart начинает выполнять main().

    mret является одной архитектурной инструкцией, поэтому программа не может увидеть наполовину выполненный переход. Но это не означает, что физический процессор обязан выполнить её ровно за один такт.

    Инструкция также обновляет служебные поля состояния прерываний. Их устройство разумнее рассмотреть позднее вместе с полным механизмом trap.

    mret не является обычным вызовом функции и не записывает новый адрес возврата в ra. В ra остаётся адрес метки spin, установленный ещё инструкцией:

    call start

    Если main() неожиданно выполнит return, управление в итоге вернётся к spin из entry.S.

    Разбор main.c¶

    #include "defs.h"
volatile static int started = 0;
void main() {
  if (cpuid() == 0) {

    // Вывод информации
    consoleinit(); // consoleinit(): Оживляет UART (микросхему последовательного порта). Теперь мы можем посылать байты в консоль.
    printfinit(); // printfinit(): Инициализирует блокировки (locks) для вывода. Это нужно, чтобы если два ядра захотят напечатать текст одновременно, буквы не перемешались в кашу.

    printf("\n");
    printf("xv6 kernel is booting\n");
    printf("\n");

    // Управление памятью
    kinit(); // kinit(): Инициализирует распределитель физических страниц. Он берет всю свободную память от метки end (из нашего линк-скрипта) до конца RAM и разбивает её на блоки по 4 КБ.
    kvminit(); // kvminit(): Создает глобальную таблицу страниц ядра. Здесь прописывается, какой виртуальный адрес какому физическому соответствует (то самое "прямое отображение").
    kvminithart(); // kvminithart(): Процессор записывает адрес таблицы страниц в регистр satp. С этого момента включается виртуальная память. 

    // Подготовка процессов и прерываний
    procinit(); // procinit(): Выделяет память под таблицу процессов (массив proc[64]).

    // trapinit() / trapinithart(): Указывает процессору, куда прыгать, если случится системный вызов или ошибка.
    trapinit();          // trap vectors
    trapinithart();      // install kernel trap vector

    // plicinit() / plicinithart(): Настройка PLIC (Platform Level Interrupt Controller). Это диспетчер прерываний от внешних устройств (диск, клавиатура).    
    plicinit();          // set up interrupt controller
    plicinithart();      // ask PLIC for device interrupts

    // Файловая система и диск
    // binit(), iinit(), fileinit(): Настройка кэша блоков, таблицы инодов и таблицы файлов. Это "скелет" для работы с файлами.
    binit();             // buffer cache
    iinit();             // inode table
    fileinit();          // file table


    virtio_disk_init(); // emulated hard disk. virtio_disk_init(): Инициализирует виртуальный диск, чтобы мы могли прочитать с него первую программу.
    userinit(); // userinit(): Создает самый первый процесс в системе.
    __sync_synchronize(); // __sync_synchronize(): Инструкция-барьер. Она гарантирует, что все предыдущие записи в память (настройка всех таблиц) физически завершились и видны другим ядрам.
    started = 1;
  } else {
    while (started == 0);
    __sync_synchronize();
    printf("hart %d starting\n", cpuid());
    kvminithart(); // Включаем виртуальную память (у каждого ядра свой регистр satp)
    trapinithart(); // Настраиваем прерывания (у каждого свой stvec)
    plicinithart(); // Подключаемся к диспетчеру прерываний
    // Каждое ядро должно лично включить у себя виртуальную память и прерывания, так как это внутренние настройки конкретного процессора.
  }
  scheduler(); //для всех хартов вызывается планировщик
}

    Функция main() получает управление от start() после выполнения инструкции mret. К этому моменту каждый hart уже перешёл из M-mode в S-mode, получил собственный стек и сохранил свой номер в регистре tp.

    На входе в main() состояние каждого hart выглядит следующим образом:

    режим привилегий = S-mode
satp              = 0, трансляция адресов выключена
sp                = стек текущего hart
tp                = номер текущего hart

    Важно, что виртуальные адресные пространства здесь ещё не разделяются. Пока satp = 0, все hart обращаются к общей физической памяти без трансляции Sv39. Затем kvminit() создаст одну общую таблицу страниц ядра, а kvminithart() установит её отдельно на каждом hart.

    hart 0 ─┐
hart 1 ─┼→ одна общая kernel_pagetable
hart 2 ─┘

    Отдельные пользовательские адресные пространства появятся позднее, когда ядро начнёт создавать процессы и их собственные таблицы страниц.

    В начале файла подключается:

    #include "defs.h"

    defs.h содержит объявления функций, реализованных в других файлах ядра:

    consoleinit()     → console.c
printfinit()      → printf.c
kinit()           → kalloc.c
kvminit()         → vm.c
procinit()        → proc.c
trapinit()        → trap.c
plicinit()        → plic.c
binit()           → bio.c
iinit()           → fs.c
fileinit()        → file.c
virtio_disk_init()→ virtio_disk.c

    main.c не реализует все эти подсистемы самостоятельно. Он задаёт порядок их инициализации. Компилятор узнаёт сигнатуры функций из defs.h, а линкер связывает вызовы с реализациями из соответствующих объектных файлов.

    Далее объявляется общая переменная:

    volatile static int started = 0;

    Она используется для синхронизации всех hart во время загрузки:

    started = 0 → общая инициализация ещё не завершена
started = 1 → общие структуры ядра готовы

    Ключевое слово static на уровне файла означает, что имя started доступно только внутри main.c. Другие исходные файлы не могут обратиться к этой переменной по имени.

    Ключевое слово volatile требует, чтобы каждое чтение и запись started действительно выполнялись через память. Без него компилятор мог бы один раз прочитать значение переменной, сохранить его в обычном регистре и повторно использовать в цикле:

    прочитать started = 0
        ↓
сохранить 0 в регистре
        ↓
больше не перечитывать память
        ↓
не заметить started = 1 от другого hart

    С volatile условие:

    while (started == 0);

    должно заново читать started на каждой итерации.

    Ограничения volatile

    volatile не создаёт блокировку, не делает переменную атомарной и не задаёт порядок остальных операций с памятью. Оно только ограничивает оптимизации компилятора для обращений к самой переменной started.

    Порядок инициализации между hart дополнительно обеспечивается барьерами __sync_synchronize().

    Поскольку started является глобальной переменной с нулевым начальным значением, она размещается в секции .bss.

    После этого начинается основная функция:

    void
main()
{

    Все запущенные hart входят в одну и ту же main(), поэтому сначала необходимо разделить их роли:

    if (cpuid() == 0) {

    В start.c номер hart был скопирован из mhartid в обычный регистр tp:

    int id = r_mhartid();
w_tp(id);

    Функция cpuid() читает это значение:

    int
cpuid()
{
  int id = r_tp();
  return id;
}

    Следовательно, условие:

    cpuid() == 0

    означает:

    tp == 0
    ↓
текущий hart имеет номер 0

    Hart 0 становится загрузочным и выполняет общую инициализацию разделяемых структур ядра. Остальные hart переходят в ветку else и ожидают её завершения:

    hart 0 → общая инициализация
hart 1 → ожидание
hart 2 → ожидание

    Дальше происходит инициализация всяких функций пояснение которых есть в приведенном вначале подглавы коде. Каждую из них я буду подробнее расмматривать далее но заострю внимание на том что происходит дальше.

    После завершения общей инициализации hart 0 должен сообщить остальным hart, что созданными структурами уже можно пользоваться:

    __sync_synchronize();
started = 1;

    __sync_synchronize() — встроенная функция GCC, создающая полный барьер памяти. В машинном коде RISC-V она превращается в инструкцию:

    fence

    Барьер не обязательно заставляет данные немедленно попасть в физическую RAM. Он запрещает компилятору и процессору переупорядочить обращения к памяти через эту точку.

    Для hart 0 устанавливается следующий порядок:

    закончить все записи общей инициализации
        ↓
__sync_synchronize()
        ↓
started = 1

    Это не позволяет сделать started = 1 наблюдаемым раньше записей, создающих таблицы, блокировки и другие структуры ядра.

    Замечание

    Компилятор и процессор могут переупорядочивать независимые операции с памятью ради производительности.

    Без барьера другой hart теоретически может увидеть started = 1 раньше, чем увидит результаты всей предыдущей инициализации, то есть:

    hart 0 создает таблицу страниц, настраивает процессы, диск и устанавливает started = 1

    hart 1 может увидеть, что started = 1, но часть таблиц ещё выглядит неинициализированной

    Hart 0:
__sync_synchronize();
started = 1;

означает,что сначала сделать видимыми предыдущие изменения
        ↓
только затем опубликовать started = 1
Остальные hart:
while (started == 0);
__sync_synchronize();
означает:
сначала увидеть started = 1
        ↓
только затем обращаться к созданным структурам

    Остальные hart выполняют ветку:

    } else {
  while (started == 0);

    Точка с запятой является пустым телом цикла:

    while (условие)
  ;

    Такой цикл называется активным ожиданием, или busy waiting. Hart не выполняет полезной работы, а непрерывно проверяет условие.

    Здесь активное ожидание допустимо, поскольку оно используется только один раз во время короткой начальной инициализации.

    После обнаружения started = 1 выполняется второй барьер:

    __sync_synchronize();

    Теперь порядок имеет обратное направление:

    увидеть started = 1
        ↓
__sync_synchronize()
        ↓
начать читать общие структуры

    Вместе два барьера образуют следующую схему синхронизации:

    hart 0:
    завершить общую инициализацию
    fence
    started = 1

hart 1 и hart 2:
    дождаться started = 1
    fence
    использовать общие структуры

    После ожидания дополнительный hart сообщает о своём запуске:

    printf("hart %d starting\n", cpuid());

    В консоли появляются сообщения:

    hart 1 starting
hart 2 starting

    Порядок этих строк не гарантирован. Допустим и такой результат:

    hart 2 starting
hart 1 starting

    Это наглядно показывает конкурентное выполнение hart.

    Далее каждый дополнительный hart выполняет собственную локальную настройку:

    kvminithart();
trapinithart();
plicinithart();

    Он не создаёт общие структуры повторно, а подключается к уже созданным hart 0 структурам:

    kvminithart()
└── установить общую kernel_pagetable
    в satp текущего hart

trapinithart()
└── установить kernelvec
    в stvec текущего hart

plicinithart()
└── настроить PLIC-контекст
    текущего hart

    После выполнения своей ветки каждый hart приходит к последней строке:

    scheduler();

    Следовательно:

    hart 0 → scheduler()
hart 1 → scheduler()
hart 2 → scheduler()

    Каждый hart выполняет собственный цикл планировщика. Планировщик ищет процесс в состоянии RUNNABLE, переводит его в RUNNING и переключает на него текущий hart.

    scheduler() объявлена с атрибутом:

    void scheduler(void) __attribute__((noreturn));

    noreturn сообщает компилятору, что функция никогда не возвращает управление вызывающему коду. Внутри неё находится бесконечный цикл, поэтому main() также никогда не заканчивается обычным return.
